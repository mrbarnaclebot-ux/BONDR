## Phase Goal

**As a** dev, **I want to** launch a coin in one Phantom signature, **so that** buyers see I hold zero launch supply.

<objective>
The enforcement point of the whole phase: sign order A co-sign (D-12), the submit route, and the settle state machine, proven with real devnet launches and a tamper run.

Purpose: LAUNCH-04 (co-sign only a matching message that contains the exit) and LAUNCH-03 (the one-tx launch lands). The mint key is the only thing that can make a launch valid, so this is where "dev holds 0" is enforced.
Output: core cosign and sendRaw, worker submit and settle with resume on boot, and devnet evidence for both exits plus a refused tamper.
</objective>

## Trust Boundaries

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-12-01 | Tampering | signed message (exit removed, recipient swapped) | mitigate | Raw byte compare against the stored message, Ed25519 verify of the dev slot, exitPresent from the stored exit, program allowlist at build; all before the mint signature (D-12) |
| T-02-12-02 | Tampering | submit replay or race | mitigate | prepared to signed transition WHERE state = 'prepared'; one signature per launch; double submit returns the current state |
| T-02-12-03 | Repudiation | launch outcome | mitigate | Every state change persisted with signature and error code before and after send |
| T-02-12-04 | Denial of service | resend of an unknown tx | mitigate | Never resend unknown before expiry; history recheck then failed (D-16) |
| T-02-12-05 | Elevation of privilege | launch while paused | mitigate | Pause re-checked in submit before cosign; server-side, not UI |
| T-02-12-06 | Tampering | wrong mint key | mitigate | mintKeyFor asserts the derived pubkey equals the reserved row |
</threat_model>
